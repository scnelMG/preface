# 원본 3D 특징점 후보 검사

AI-578의 첫 단계에서 생성 GLB의 기존 템플릿 특징점과 피부 메시를 대조한다. FN-REC-02의 원본 3D를 입력으로 삼고, FN-CON-01의 상담 전송 경로와 분리한다.

원본 파일과 신뢰할 수 있는 원본 승인 해시를 사용한다. 도구는 양쪽 눈 안쪽·콧볼·광대·턱과 이마에서 턱끝까지의 후보를 대조한다. 빠진 점, 같은 템플릿 번호의 서로 다른 좌표, 비유한 좌표, 좌우가 뒤집히거나 두 점이 겹친 경우를 구별한다.

`candidate`는 피부에서 두 점이 올바른 축 순서로 읽혔다는 뜻이다. 모든 결과의 해부학적 품질은 `unverified`다. 출력에는 후보 상태만 있으며 파일 경로, 해시, 좌표, 길이, 얼굴 이미지가 포함되지 않는다. 검토 허가를 받은 생성 모델의 정면·사선·측면에서 특징점의 실제 위치와 반복 측정 오차를 확인한 뒤 수치 표시를 연결한다. 특히 콧볼 주름 후보를 최외곽 콧볼점으로 사용하려면 위치를 따로 확인한다.

```sh
node --test services/gpu-worker/reconstruction/tools/baseline-landmark-audit.test.mjs
```

## 개발 생성 모델 검수 (2026-11-07)

개발의 승인된 생성 GLB 3개에서 원본·리그 해시, fit 결속, 엔진·리그·토폴로지 버전과 스키마를 확인했다. 좌표를 다시 읽어 정면의 가로·세로 축 투영값과 무단위 비율을 비교했다. 코 측면은 승인 리그의 nasion·subnasale·pronasale 좌표와 코 높이 기준을 대조했다.

| 항목 | 결과 |
| --- | --- |
| 특징점 후보 | 눈 안쪽·콧볼·광대·턱·이마부터 턱끝까지 5쌍 모두 3개 원본에서 유한하고 올바른 축 순서로 읽혔다. |
| 비율 재현 | 턱 너비 ÷ 광대 너비, 이마부터 턱끝까지 높이 ÷ 광대 너비, 콧볼 후보 너비 ÷ 눈 안쪽 거리가 모두 반복 계산에서 일치했다. |
| 콧볼 경계 | 49·279 후보를 코 리그에 매핑했을 때 6점 모두 승인 리그의 폭 기준점과 달랐고 더 안쪽에 있었다. 이 후보로 콧볼 폭을 표시하거나 조절 방향을 제안하면 안 된다. |
| 코 측면·단위 | 3개 모두 승인 리그의 코 높이 산식이 재현됐다. 실측 스케일을 확인한 모델은 0개였다. |

반복 계산은 숫자의 재현성을 확인한다. 해부학적 정확도는 동일 원본에 정면·사선·측면 기준점을 표시한 참조값과 비교해 판정한다. 콧볼 최외곽점과 콧볼 주름점은 구별하고, 승인 리그의 폭 기준점도 참조값에 대조한다. [FaceBase 특징점 정의](https://www.facebase.org/resources/human/facial_norms/notes/)

검수는 개발 서버의 읽기 전용 경로에서 수행했고 원본 메시·개별 좌표·개별 측정값을 검수 기록에 남기지 않았다.

## 콧볼 최외곽점 참조와 측정 저장

콧볼 최외곽점은 좌우 콧볼 피부에서 각각 바깥으로 가장 돌출된 지점이다. 정면에서 가로 위치를 맞추고 비저면에서 콧볼과 볼이 만나는 주름 및 비공 가장자리와 구분한다. 같은 원본에서 서로의 표시를 보지 않은 두 검수자가 각각 양쪽 콧볼점과 눈 안쪽점을 기록한다. 가로 너비는 같은 3D 좌표계의 X축 차이로 계산한다. 승인 코 리그의 조절점은 검수 대상을 찾는 데 쓸 수 있지만 참조점은 아니다. [FaceBase 특징점 정의](https://www.facebase.org/resources/human/facial_norms/notes/)

눈 안쪽점은 정면에서 위·아래 눈꺼풀이 만나는 안쪽 점으로 잡는다. 흰자위가 끝나는 위치와 구분하고, 내안각 주름이 가리면 주름과 눈꺼풀 틈이 만나는 위치를 확인한다. [FaceBase 특징점 정의](https://www.facebase.org/resources/human/facial_norms/notes/#endocanthion-right-and-left)

### 검수 기록 만들기

파일 접근 권한이 있는 검수 환경에서 설치된 `three`의 경로를 지정해 아래 명령을 실행한다. 출력한 루프백 주소를 열고 승인된 원본 GLB를 선택한다. GLB는 브라우저 메모리에서 읽는다. 화면에는 기존 후보와 다른 검수자의 표시가 나오지 않는다.

```sh
node services/gpu-worker/reconstruction/tools/baseline-reference-review.mjs apps/web/node_modules/three
```

검수자마다 정면과 아래쪽을 대조하고 네 점을 표시한 뒤 별도 JSON을 저장한다. 브라우저 저장 위치도 비공개 폴더로 지정한다. 두 JSON 객체를 한 배열로 묶는다. 각 객체에는 원본 승인 해시 `meshSha256`, 검수자 가명 `reviewer`, 시점 확인 `frontal: true`와 `basal: true`, 피촬영자 오른쪽부터 기록한 배열 `alar`와 `innerEye`가 들어간다. 화면에서 내보낸 `vertexSpace: "skin-primitive-index"`는 원본 피부 primitive의 정점 번호를 뜻한다. 세분화된 GLB에서는 서로 다른 정점이 같은 템플릿 번호를 가질 수 있어 화면에서 고른 정점을 그대로 사용한다.

두 검수자의 너비 범위와 눈 안쪽 거리로 정규화한 콧볼·눈 안쪽 후보의 좌우 가로 오차를 계산한다. 양수는 후보가 참조점보다 안쪽에 있음을 뜻한다. 두 검수의 범위는 관찰된 편차이며 정확도 합격 한계나 실제 길이 단위가 아니다. 비교할 두 너비의 범위가 겹치면 방향을 보류한다.

입력과 결과는 접근 권한을 제한한 검수 폴더에 둔다. 새 보고서를 저장한 뒤, 재조회 시 같은 원본·검수점에서 다시 계산한 결과와 대조한다. 원본 해시가 바뀌거나 보고서가 달라지면 재조회 검증이 실패한다. 제품 API와 상담에는 독립 검수 및 허용 오차 판정 후 연결한다.

```sh
node services/gpu-worker/reconstruction/tools/baseline-landmark-audit.mjs <원본GLB> <승인해시> save-review <검수JSON> <새보고서JSON>
node services/gpu-worker/reconstruction/tools/baseline-landmark-audit.mjs <원본GLB> <승인해시> verify-review <검수JSON> <보고서JSON>
```

개발 생성 모델 3개를 추가 진단한 결과, 49·279 후보와 리그 조절점의 가로 차이는 코 높이 대비 0.078~0.121이었다. 이는 두 기준 사이의 차이이며 독립 검수점에 대한 오차는 아직 산출하지 못했다. 합성 모델에서는 검수 기록 저장·재조회와 다른 해시가 저장된 보고서의 거절을 확인했다.

같은 개발 표본에서 코끝과 코밑점 사이의 양쪽 표면 법선으로 후보를 따로 골랐다. 6점에서 기존 49·279 후보의 가로 편차는 코 높이 대비 −0.0127~+0.0214였다. 두 가로 탐색 폭에서 선택은 같았다. 눈은 피부 경계의 닫힌 고리와 눈 주변 표면 굴곡으로 각각 시험했으나, 좌우 한 쌍을 모두 확보한 모델은 0개였다. 코의 수치는 두 자동 후보의 차이로만 기록한다. 표면 형상 후보는 별도로 표시한 해부학적 참조점과 대조해야 한다. [Jia 외 3D 특징점 검증](https://homes.cs.washington.edu/~shapiro/Multimedia/jia-embclandmarks_final.pdf)

Jira AI-578·579와 선행 이슈의 첨부·검수 기록, 저장소 및 Notion의 코 모델링 개선·PoC 기록에서 해당 원본의 독립 표시 파일을 찾지 못했다. 공개 합성 모델은 Chrome에서 네 점 표시·두 시점 확인·JSON 내보내기를 확인했고, 내보낸 형식으로 보고서 저장·재조회도 확인했다. 합성 시험의 두 번째 기록은 입출력 확인용이다.
