# 자유 입력 상담·편집 적용 계약안 (S15P31B204-75)

2026-10-23. 편집 담당자가 확정한 **제품 동작과 상담·적용 경계**를 API v2.9의 CON-01·EDIT-05에 대조한 계약이다. 서비스 구현 완료를 뜻하지 않는다. 효과 의미와 좌우 기준은 Jira -71의 효과 계약을 따른다.

## 확정된 사용자 동작

- 자유 입력과 예시 칩을 모두 받는다. 명확한 요청은 작은 단계로 바로 적용하며 대화와 슬라이더로 이어서 조절한다. 모호하거나 모순되면 적용 전 선택지를 묻는다.
- 지원 효과 여럿은 한 거래·undo 1회다. 미지원 효과가 섞이면 가능한 부분만 적용하고, 미적용 구절과 이유를 함께 보여 준다. 모두 미지원이면 얼굴을 바꾸지 않는다.
- 1차 눈 요청은 양쪽에 함께 적용한다. “더/덜”은 직전 성공 거래의 효과 전체를, 특정 부위를 지목하면 그 효과만 조절한다. 한쪽 눈만 바꾸라는 요청은 적용하지 않는다.
- 상담 답변·After·슬라이더·최근 변경 카드는 **저장 성공 후 실제 적용값**으로 갱신한다. 저장 전 해석 결과는 적용 성공으로 말하지 않는다. 되돌린 뒤에도 기존 대화는 남기고 취소 기록을 추가한다. 슬라이더·점 조작은 채팅에 자동 기록하지 않는다.

## 1차 출시 범위 — 코와 지원 모델의 눈 (2026-11-01)

코의 채팅·슬라이더·점 조작은 기존 네 조절을 유지한다. 눈은 화면의 쌍꺼풀 모양(인라인·인아웃·아웃라인)·높이와 양쪽 앞·뒤·윗·밑트임만 채팅·직접 조절에 연결한다. 쌍꺼풀 깊이는 엔진 기본값으로 고정하고 눈매교정(눈 뜨임)·한쪽 눈 편집은 열지 않는다. 눈 저장값은 기존 `eye.double_lid_depth` 등의 morph code가 아니라 눈별 `eyeEdit` 상태다. 화면의 `%`는 모델별 승인 한계에 대한 비율이고 눈 상태의 엔진 값은 0~100이다.

눈별 쌍꺼풀 판정이 없는 모델은 눈 기능 전체를 잠근다. 이미 쌍꺼풀이 있는 눈에는 새 라인을 만들지 않고 트임만 허용한다. 눈별 판정·같은 모델/리그 버전의 승인된 안전 범위·최종 형상 검사·서버 `eyeEdit` 저장이 준비된 모델에서만 눈 후보를 적용한다. 그 전에는 눈 요청을 다른 눈 morph code나 코 효과로 바꾸지 않고 미지원으로 알린다. 코+눈 혼합 요청은 지원·형상 검사를 통과한 항목만 한 거래로 저장하고 나머지를 `skipped[]`에 남긴다. 코 모델의 서버 형상 검사가 준비되지 않았으면 기존처럼 채팅 적용을 `EDIT_030`으로 거절한다. `chat_apply_ready`는 검증 전 수동으로 켜지 않는다.

상담 후보를 만든 뒤 적용 전에 눈 판정·승인 범위가 사라지거나 다른 버전으로 바뀌면, 이미 제안한 혼합 코+눈 거래 전체를 거절한다. 코 부분만 뒤늦게 적용해 다른 결과를 성공으로 표시하지 않고 최신 모델 지원 상태로 다시 상담한다.

슬라이더도 최종 메시 검사와 모델별 승인 범위를 사용한다. 승인 정보가 없는 모델의 슬라이더 저장은 `EDIT_031`(409)로 거절하고 FE 미리보기를 버린다. 기존 공통 DB 범위만으로 허용하던 1차 임시 예외는 검사 경로가 배포된 뒤 종료한다.

1차 상담 후보와 슬라이더의 세부 기능·표시 기준은 [효과 계약의 1차 노출 규칙](effects-v1.md#값과-지원-범위)을 따른다. 화면에 없는 효과는 상담에서 적용하지 않는다.

## 현재 슬라이더의 상담 연결 (2026-11-05, S15P31B204-502)

현재 화면에서 실제로 열린 윤곽 여섯 조절(`contour.cheekbone`, `contour.cheek_volume`, `contour.chin_projection`, `contour.chin_length`, `contour.chin_width`, `contour.jaw_angle`)과 체중 변화(`contour.weight_shape`)를 같은 저장 코드로 상담한다. `+`는 광대·볼살·턱끝 길이/폭·사각턱 확대, 턱끝 전방, 체중 변화의 증량 방향이며 `-`는 반대 방향이다. 체중 변화는 실제 체중 수치나 건강 결과를 예측하지 않는다.

생성 모델의 윤곽은 검증된 GLB 타깃, 체중은 체중 변화 승인 결속을 확인한다. 코는 `chat_apply_ready`와 코 승인을 요구하고, 눈은 직접 조절과 같은 모델별 눈 승인과 형상 검사를 사용한다. 체중 변화는 눈·코·다른 윤곽·점 변위와 동시에 저장하지 않는다. 모호한 부위·방향, 한쪽 지시, 체중 변화와 다른 조절의 혼합 요청은 먼저 되묻고 변경 요청을 만들지 않는다. kg 지정 요청은 실제 체중과 얼굴 변형의 검증된 대응이 없어 적용하지 않고 상대 방향 조절을 안내한다. 서버는 후보 코드를 카탈로그와 모델 지원 상태로 다시 검사하고, 실제 저장 성공 뒤에만 적용 카드·이력·슬라이더를 갱신한다.

답변은 `AI 실장님`의 짧은 존댓말로 하고, 미지원·의료 판단·인물 모사·범위 밖 요청에는 이유와 가능한 조절 방법을 알려 준다. 답변에서 저장 전 성공을 주장하거나 열린 눈·윤곽을 무시해 “코만 가능”하다고 안내하지 않는다. 합성 문장·오분류·거절·거짓 성공 사례는 상담 회귀 테스트에서 확인한다. 실제 사용자 발화와 생성 얼굴의 시각적 품질 평가는 별도 검증이다.

품질 규칙은 [OpenAI Prompting](https://developers.openai.com/api/docs/guides/prompting)의 명시적 역할·톤 지시, [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)의 스키마 외 의미 검증, [Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)의 대표·경계·적대 입력 회귀를 참고했다. 스키마 적합만으로 부위·방향·저장 성공의 정확성을 주장하지 않는다.

## 직접 조절과 같은 상담 명령

- `처음으로`는 초기화 명령으로 처리한다. `쌍꺼풀을 없애줘`는 해당 모델의 무쌍 눈에 추가한 미리보기 라인만 끈다. 눈 트임과 저장된 라인 설정은 보존한다.
- 화면 항목 이름과 값을 하나만 명시하면 Spring이 직접 읽어 `actions[].target`에 화면 전체 범위 대비 절대값을 넣는다. 저장은 현재 모델의 승인 범위, 코끝 결합 비율과 눈 슬라이더 단위를 사용한다. 예전 후보의 상대 강도 필드는 그대로 읽는다. 체중 변화는 화면에 표시하는 미리보기 강도를 사용한다.
- 직접 조절 항목을 골라 상담하면 CON-01에 `directControl: { code, stateVersion }`을 보낸다. 서버는 선택한 시안 버전과 편집 가능 범위를 확인한다. 분명한 방향만 선택 코드의 후보로 만들고, 다른 부위·모호한 요청·버전 불일치에는 편집 없이 안내한다. EDIT-05에서도 후보의 버전을 다시 확인한다.
- 상담 중 체중 변화와 얼굴 조절을 전환할 때는 원본으로 돌아가는 항목을 먼저 보여 준다. 전환만 확인하면 직접 조절과 같은 API를 호출한다. 생성 시안에서 후속 조절까지 확인하면 CON-01의 `modeSwitch: { target: "toWeight" | "toFace", stateVersion }`에 확인한 방향과 버전을 싣는다. EDIT-05는 전환 후 기준으로 요청을 검사하고 한 이력으로 저장한다. 취소·상태 변경·후속 조절 실패 시 시안은 유지된다.

## 상담 실행 위치 — Spring 직접 실행 (2026-10-26)

`API-CON-01`의 상담 의도 해석과 GMS 호출은 Spring에서 실행한다(S15P31B204-369). 별도 FastAPI 상담 서버와 `AI_BASE_URL`, 내부 상담용 HTTP `INT-AI-01`은 이 경로에서 사용하지 않는다. `API-CON-01·02`의 FE 요청·응답, 변경 요청 저장 및 `API-EDIT-05`의 적용 경계는 유지한다. GMS는 지원되는 코·눈 편집 **후보**만 만들고 실제 3D 적용값이나 성공 여부를 결정하지 않는다. Runpod GPU 워커의 얼굴 생성·결정적 최종 메시 형상 검사(`INT-AI-02`)는 별도 경계다.

Spring은 문장과 검증된 텍스트 문맥만 GMS로 보낸다. 얼굴 사진·영상·3D 이미지, 미검증 측정값은 보내지 않는다. GMS 키는 서버 환경 변수에만 둔다. 응답은 원문 근거·마스킹·모델별 지원 코드와 눈 조절·좌우·강도·부분 미지원·거짓 성공 문구를 서버에서 다시 검사한다. 잔액 확인 실패·한도 부족·타임아웃·형식 위반은 `CON_002`(시간 초과) 또는 `CON_003`(그 밖의 장애)으로 처리하고, CON-01의 사용자/도우미 메시지나 얼굴을 저장하지 않는다. 요청별 중복 호출 경계는 아래 1.3절을 따른다.

## GMS 중복 호출 경계 (2026-10-27)

`API-CON-01`의 `requestId`는 선택적 UUID다. FE는 매 전송에 만들고 같은 전송의 네트워크 재시도에는 유지한다. Spring은 GMS 호출 직전 공유 Redis 키 `consult:gms:<simulationId>:<requestId>`를 7일간 선점한다. 중복 ID는 GMS를 다시 호출하지 않고 `CON_011`(409)을 반환한다. FE는 대화 내역을 확인하며 자동 재시도하지 않는다. 타임아웃처럼 GMS 처리 여부를 알 수 없는 경우에도 키를 지우지 않는다. 기존 클라이언트가 ID를 보내지 않으면 호환을 위해 요청은 받지만 재시도 중복 방지는 보장하지 않는다. 로컬 규칙·고정 명령은 GMS 호출이 없어 이 선점 대상이 아니다.

### 같은 시안의 새 상담 (S15P31B204-810)

`POST /api/v1/simulations/{simulationId}/messages/new-conversation`은 본인 시안에서 새 상담을 시작한다. 응답의 `conversationAfterSeq`는 현재 대화의 경계값이다. 얼굴 편집값·편집 버전·되돌리기 순번은 유지한다. `GET /messages`는 현재 대화와 경계값을 반환하고, `archived=true`일 때 같은 페이지 형식으로 이전 대화만 반환한다.

웹은 전송 요청에 경계값을 포함한다. 서버는 대화가 바뀌었으면 이전 전송 결과를 저장하지 않고, 이전 선택지와 적용되지 않은 편집 후보도 새 대화에서 거절한다. 저장이 이미 완료된 편집은 얼굴 편집 이력으로 보존한다.

GMS 입력·출력·추론 토큰, 잔액 전후, 관측 차감과 지연은 상담 원문·개인 측정값 없이 기록한다. 잔액 차이는 정수 반올림·동시 호출의 영향을 받으므로 호출별 확정 과금액으로 해석하지 않는다. 현재 개발 배포는 API 인스턴스 1개라 잔액 예약은 인스턴스 안에서 직렬화한다. 다중 API 인스턴스로 확대할 때 공유 예산 예약으로 바꾸기 전에는 확장하지 않는다(S15P31B204-302).

## API v2.9에서 재사용할 경계와 변경안

기존 `POST /simulations/{simulationId}/messages`(CON-01)와 `POST /simulations/{simulationId}/change-requests/{requestId}/apply`(EDIT-05)를 유지하는 **최소 변경안**이다. FE가 `COMPLETE`에 대해 확인 버튼 없이 apply를 이어서 호출한다. 질문·미지원만 있을 때는 apply하지 않는다.

| 현재 v2.9 | 필요한 변경 | 이유 |
| --- | --- | --- |
| CON-01은 예시 문장 1차, 자유 문장 2차 | `content`에 둘 다 허용 | 자유 입력 확정 |
| `ChangeRequest`는 `part/subPart/direction/degree` 단일 조절 | `actions[]`(효과·좌우·방향·강도), `skipped[]`(원문 구절·이유) | 복합·부분 적용 |
| CON-01 assistant 응답과 EDIT-05 적용이 별도 | CON-01은 후보 또는 질문만 표현; 성공 문구는 EDIT-05 성공 응답의 실제값으로 생성 | 실패 시 거짓 성공 방지 |
| INT-AI-02는 공통 범위 clamp | 서버가 같은 원본 모델·리그로 최종 형상을 검사해 실제값을 결정하고 Spring에서 다시 검증 | 화면·저장 불일치 방지 |
| EDIT-05 `changes[]/clamped/summary` | 각 효과 `applied[]`의 from/to/limited, `skipped[]`, 새 `stateVersion`·`seq` | 화면·undo·대화의 동일한 근거 |

AI는 정점 좌표를 출력하지 않고 편집 **후보**만 만든다. FE는 같은 원본 모델에 후보를 미리 적용해 즉시 보여 줄 수 있지만, FE가 보낸 조절값이나 형상 검사 결과를 저장 권한으로 신뢰하지 않는다. Spring은 소유권·요청 ID·`stateVersion`을 확인한 뒤 서버의 결정적 편집 엔진(INT-AI-02, GMS 호출 아님)이 같은 모델/리그와 `capabilities`로 계산·검사한 **실제값**을 받는다. Spring은 허용 code·좌우·유한값·범위·모델/리그 버전과 후보/결과의 일치를 다시 확인하고 변경 전체를 `morph_change` 한 거래로 저장한다. FE는 저장 성공 응답으로 After·카드·슬라이더를 맞추고, 실패 시 미리보기를 폐기해 최신 상태를 다시 읽는다. 서버 형상 검사가 준비되지 않은 모델은 채팅 자동 적용을 열지 않는다. 이 기준은 수치 clamp만 하는 현 BE 구현의 보장을 확대해 말하지 않기 위한 서비스 이식 조건이다.

```json
  "requestId": "example-request", "status": "COMPLETE", "schemaVersion": "v2",
  "actions": [
    {"code": "nose.tip_projection", "side": "both", "direction": 1, "strength": "small"},
    {"code": "nose.tip_height", "side": "both", "direction": -1, "strength": "small"}
  ],
  "skipped": []
}
```

FE는 현재 `stateVersion`과 `requestId`로 EDIT-05를 호출한다. Spring과 서버 편집 엔진이 실제값을 결정·저장한 성공 응답의 예:

```json
{
  "morphState": {"schemaVersion": "v2", "weights": {"nose.tip_projection": 0.12, "nose.tip_height": -0.09}},
  "stateVersion": 4, "seq": 3,
  "applied": [
    {"code": "nose.tip_projection", "from": 0, "to": 0.12, "limited": false},
    {"code": "nose.tip_height", "from": 0, "to": -0.09, "limited": true}
  ],
  "skipped": [], "canUndo": true, "canRedo": false
}
```

## 적용·복원 규칙

- 코 v2 변경 요청은 `actions[]`와 `skipped[]`를 사용한다. 눈 후보는 같은 변경 요청 안에서 화면의 `eyeEdit` 필드에만 매핑하며 좌우 미지정은 양쪽에 적용한다. 코 효과는 좌우를 나누지 않는다. 모호한 요청은 `options[]`만 반환하고 편집 후보를 비운다. 구 v1의 단일 `part/subPart/direction/degree` 요청과 저장 상태는 읽기만 유지하고 새 눈 상태로 임의 변환하지 않는다.
- 화면의 변경 카드는 별도 `cards[]`를 저장하지 않고 EDIT-05의 `applied[]`와 `skipped[]`에서 만든다. `options[]`의 선택 ID는 시안·모델/리그 버전·`stateVersion`에 묶어 저장하고, 그중 하나라도 바뀐 뒤 누른 옛 선택지는 적용하지 않고 다시 묻는다.
- 지원 밖 구절은 `skipped[]`에 원문 구절과 이유를 남긴다. 지원 효과가 남으면 그것만 한 거래로 적용한다. 모델별 형상 검사에서 줄어든 값은 `applied[]`의 `to`와 `limited`에 기록한다. 안전한 결과가 없는 요청은 적용·undo 이력을 만들지 않고 이유를 알린다.
- 눈 후보의 `source`는 선택적인 원문 구절이다. 적용 시 한계에 걸려 눈 값이 바뀌지 않았다면 저장된 사용자 문장에 실제 포함된 구절만 `skipped[]`의 근거로 쓴다. 예전 후보나 더/덜 요청처럼 근거가 없으면 새 구절을 만들어 내지 않고 제한 안내만 표시한다.
- CON-02는 저장된 `applyResult`의 `applied[]`·`skipped[]`·요약·`seq`를 그대로 복원한다. AI가 후보를 해석했거나 FE 미리보기가 보였다는 이유만으로 성공 메시지를 저장하지 않는다.
- AI 실패·시간 초과로 CON-01이 실패하면 사용자/도우미 메시지와 얼굴을 저장하지 않는다. CON-01 성공 후 EDIT-05가 실패하거나 `stateVersion`이 충돌하면 이미 저장된 사용자 메시지는 남길 수 있지만 적용 성공 메시지·카드는 남기지 않고 요청을 재확인하게 한다.
- 임의 표면 점의 자유 변위는 `actions[]` 효과 코드가 아니다. 코 점 배열은 [자유 제어점 계약](point-strokes-v1.md)에 따라 공통 시안 상태·형상 검사·undo에 들어간다.

BE·FE는 이 계약의 필드와 사례를 각 구현에 반영하고, 기획 담당은 API 명세를 갱신한다. 서비스 끝단의 형상 검사·복원·오류 사례가 통과하기 전에는 기능 구현 완료로 표시하지 않는다.

추천 답변의 비교 버튼은 `exampleId: consult-preview` 요청에 사용자에게 보일 `content`와 선택한 `comparisonTarget: { code, value }`를 따로 보낸다. `value`는 슬라이더 표시값을 -1~1로 환산한 값이다. 서버는 시안에서 지원하는 코드와 모델의 범위를 적용하고, 사용자가 비교를 적용하기 전에는 편집값이나 되돌리기 이력을 저장하지 않는다. 자유 입력과 기존 클라이언트는 이 필드를 생략한다.

추천 요청은 선택적으로 `recommendationMeasurements`에 사용자 시안의 3D 참고 비율을 보낸다. 서버가 허용한 후보에 연결된 유한한 비율만 GMS에 전달한다. GMS가 자료에 근거해 후보를 최대 세 개 고르면, 서버가 조절·측정·자료 ID를 대조하고 중복 후보를 제외한다. 현재 시안에서 내부 시험한 다음 조절 요청은 `trial-version: 1`, `trial-state: <시안 버전>`, 원래 비율, `<후보 ID>:down` 또는 `<후보 ID>:up`의 시험 비율을 같은 맵에 담는다. 서버는 버전, 조절 지원과 전후 비율을 검사하고 GMS가 돌려준 방향을 시험 목록에서 확인한다. 상담 답변의 `profileSection`은 선택된 ID 순서대로 `:measured:<방향>/<전>/<후>,…`를 붙일 수 있다. 같은 순서의 설명을 답변 본문 줄 단위로 저장한다.
