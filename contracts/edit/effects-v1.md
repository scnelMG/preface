# 눈·코 편집 효과 계약안 (S15P31B204-71)

2026-10-23. 눈·코 편집 담당자가 **제품 동작과 아래 v2 효과 코드·좌우·값 의미**를 확정했다. 이 문서는 BE API v2.9와 동료 모델링 PoC 사이의 공통 기준이다. 현재 BE·FE 구현이 이 계약을 이미 지원한다는 뜻은 아니며, 적용 결과와 모델별 지원 여부는 서비스 통합 검증이 필요하다.

## 제품 동작

- AI·슬라이더·이름 붙은 조절점은 같은 효과와 현재 값을 사용한다. 임의 표면 점 드래그는 별도 변위지만 같은 시안 저장·형상 검사·되돌리기를 사용한다.
- 눈의 좌우는 **사용자 본인 기준**이다. 저장 상태는 눈별로 구분하지만 1차 화면·상담의 트임은 양쪽을 함께 조절하며 한쪽만 바꾸지 않는다. 코는 현재 PoC에서 좌우를 분리하지 않는다.
- `0`은 원본 상태다. 저장·슬라이더·변경 카드·챗봇 답변에는 요청값이 아닌 **실제 적용값**을 반영한다. 여러 효과는 한 거래로 저장하고 한 번에 되돌린다.
- 모델에 없는 효과는 미지원으로 알린다. `eye.double_lid_depth`는 기존 쌍꺼풀 홈의 진하기이며 인아웃 형태나 선 높이가 아니다. `nose.alar_width`는 콧볼 겉면 폭이며 콧구멍 테두리 모양이 아니다. 이들을 같은 효과로 대체하지 않는다.

## 효과 의미와 서비스 저장 코드

`+` 방향은 표의 방향이고, 반대 요청은 음의 방향이다. **아래 눈 morph 코드는 이전 v2 계약이며 1차 눈 화면·상담의 저장 형식이 아니다.** 1차 눈은 눈별 `eyeEdit`에 쌍꺼풀 사용 여부·모양·높이와 트임 4종을 저장하고, 깊이는 엔진 기본값으로 고정한다. PoC 내부 키는 뷰어 구현 키로 둔다. 기존 v1 저장 상태는 읽을 수 있도록 유지하며, 가정 항목 `eye.size`와 좌우 없는 `eye.tail_angle`을 새 눈 상태로 자동 변환하지 않는다.

## 값과 지원 범위

1차 코 조절은 콧대 높이·코끝 앞뒤·코끝 위아래·콧볼 너비 네 항목이다. 코끝 위아래의 저장용 그룹값 `u`는 `nose.tip_height=-0.6u`, `nose.tip_rotation=-0.4u`로 묶는다. 상담도 같은 네 코 조절만 후보로 만들며, 코끝 위아래 요청 하나는 높이·회전 두 저장값을 같은 비율로 한 거래에 넣는다. 다른 v2 코 코드는 계약에 남기되 1차 상담 후보로 만들지 않는다.

1차 눈 조절은 쌍꺼풀 모양(인라인·인아웃·아웃라인)·높이와 양쪽 앞·뒤·윗·밑트임이다. 눈별 상태는 `{enabled, style, values, curve}`로 저장하고, `values`의 높이·트임은 엔진 단위 0~100이다. 화면 `%`는 같은 모델의 승인된 안전 한계에 대한 비율이다. 이미 쌍꺼풀이 있는 눈은 새 라인을 만들지 않고 트임만 제공하며, 눈별 판정이 없거나 승인 범위가 없는 모델은 눈 편집을 잠근다. 눈매교정·쌍꺼풀 깊이·한쪽 트임은 이번 화면과 상담에서 제공하지 않는다.

기존 생성 모델은 `morphSchemaVersion=v1`을 유지한다. V13은 v1 카탈로그에 누락된 `nose.tip_projection`·`nose.tip_rotation`을 **선택적 저장 코드**로 추가한다. 코드가 생겼다는 이유만으로 기존 모델을 열지 않으며, 원본 GLB·리그와 코 5코드의 모델별 승인 및 요청마다 실행하는 최종 메시 검사를 통과해야 네 조절을 활성화한다. 기존 시안의 상태·이력은 변환하지 않는다.

화면의 `−100%~+100%`는 모델별 승인 범위의 양 끝이고 `0%`는 원본이다. 예를 들어 승인 범위가 `[-0.25, 0.4]`이면 화면 `−100%`는 저장값 `−0.25`, `+100%`는 `0.4`다. 코끝 내림도 화면 비율을 그룹값 `u`의 승인 범위로 변환한 뒤 위 비율을 적용한다. 저장·최종 메시 검사는 실제 상대값으로 처리하고, 화면의 슬라이더·적용 카드·변경내역은 승인 범위에 대한 비율로 표시한다. 승인되지 않은 효과는 슬라이더와 상담에서 모두 미지원이며, 이 표시 변환은 안전 범위를 넓히지 않는다.

서비스 `weight`는 상대 조절값이다. PoC 코 조절의 내부 길이·비율·각도 수치를 그대로 넣거나 화면에 mm·의학적 수치로 표시하지 않는다. 모델별 리그와 `case_limits`, 복합 편집 후 최종 메시 검사가 실제 적용 가능량을 결정한다. `morph_parameter.min/max`는 DB 범위 검증이며 메시 접힘·외관 검사가 아니다. 모델별로 지원 효과, 좌우, 단위, 범위, 모델/리그 버전을 조회할 수 있어야 한다.

v2의 공개 `weight`는 모델별 한계에 대한 상대값으로 정한다. 양방향 효과는 `[-1, 1]`, 원본에서 진해지기만 하는 쌍꺼풀 홈·애교살은 `[0, 1]`, 누락 키는 `0`이다. 뷰어는 부호별 모델 한계에 `|weight|`를 곱해 PoC 내부값으로 바꾸고, 역변환해 저장·재조회 후 같은 얼굴이 나오는지 검증한다. 화면의 `%`는 **조절 범위에 대한 비율**이며 신체 치수의 증감률이 아니다. 최종 메시 검사에서 축소되면 요청값 대신 역변환한 실제값을 저장한다.

현재 `GET /morph-parameters?schemaVersion=`의 공통 범위만으로 특정 얼굴의 지원 여부를 알 수 없다. 서비스 이식 시 `GET /simulations/{simulationId}`에 해당 원본 모델의 `capabilities`(지원 코드·좌우별 실제 상대 범위·모델/리그 버전)를 함께 제공한다. FE는 공통 카탈로그와 이 목록의 교집합만 조절 가능하게 하고, AI도 같은 목록 밖의 효과를 성공으로 말하지 않는다. 키가 있는 것만으로 지원을 선언하지 않고 해당 모델의 최종 형상 검사를 통과해야 한다. 비로그인 공개 샘플은 서버 시안이 없으므로 샘플 자산에 같은 형식의 정적 목록을 둔다.

## 윤곽 (S15P31B204-564 후속)

윤곽 조절은 코 엔진·리그 없이 **GLB morph target 쌍**으로 움직인다. 저장 코드 `contour.<이름>`의 음수 값은 `<code>_neg`, 양수 값은 `<code>_pos` 타깃 가중치 `|weight|`로 그린다. 타깃은 gpu-worker `reconstruction/tools/contour_morphs.py`가 GNM 위상(`_TEMPLATE_INDEX`)의 GLB에 희소 저장으로 덧붙인다. 사각턱은 모델마다 턱 아래가 꺾이는 선을 다시 찾아 맞춘다. 신규 모델은 두 방향의 최종 메시를 각각 검사해 통과한 표본까지 변위를 축소해 굽는다. 양쪽이 모두 검증된 코드만 남긴다. 이 값은 시뮬레이션 범위다. [윤곽 검사](../../docs/ai/contour-final-mesh-validation.md)

시안 상세(EDIT-03)의 `editRanges`는 현재 모델이 지원하는 값만 담는다. `weights`는 코·윤곽·체중 저장 코드별 `{min,max}`이고 `eyes`는 트임과 모양별 높이 키의 `{min,max}`다. 코는 모델별 승인과 카탈로그의 교집합을 사용한다. 눈은 모델 승인 엔진 단위를 사용하고, 쌍꺼풀은 별도 눈 판정과 현재 모양을 함께 확인한다. 윤곽과 체중은 검사 범위를 GLB 변위에 반영한 뒤 정규화한 가중치를 사용한다. 신규 윤곽의 형상 검사값은 현재 GLB와 결속한 `contour_morphs.measured_limits`에서 확인한다. 기존 GLB는 기존 승인과 타깃 쌍으로 지원을 판정한다. 편집 모드 잠금과 저장 검사도 적용한다.

| 서비스 저장 코드 | 화면 이름 | 음수(−) | 양수(+) | 묶음 변형 |
| --- | --- | --- | --- | --- |
| `contour.cheekbone` | 광대 | 줄이기(안쪽·위로) | 키우기 | 앞광대 + 옆광대 |
| `contour.cheek_volume` | 볼살 | 줄이기 | 채우기 | 광대 바로 아래 볼 |
| `contour.chin_projection` | 턱끝 앞뒤 | 뒤로 | 앞으로 | 턱끝 + 아래턱 일부 |
| `contour.chin_length` | 턱끝 길이 | 짧게 | 길게 | 턱끝 위아래(+약간 앞) |
| `contour.chin_width` | 턱끝 폭 | 좁게 | 넓게 | 턱끝 좌우 |
| `contour.jaw_angle` | 사각턱 | 좁게 | 넓게 | 턱선 0.8 + 턱 근육 0.48 |

- 카탈로그(V21): v1·v2 모두 `part=CONTOUR`, 범위 `[-1, 1]`, step `0.01`. 서버는 이 범위로만 clamp한다. 코 검사기(INT-AI-02)에는 보내지 않으며, 코가 그대로인 저장은 검사기를 부르지 않는다. 코를 함께 바꾸면 검사기는 코 값만 보고 윤곽 값은 요청값 그대로 남는다.
- 지원 여부: 코 승인(`capabilities`)과 별개다. FE는 GLB에 해당 타깃 쌍이 있는 윤곽 코드만 연다. 신규 생성 모델은 워커가 코·눈 승인 계산 **전에** 타깃을 구워 올린다(승인 결속 `meshSha256`이 GLB 전체 바이트 해시이므로). 굽기가 실패하면 윤곽 없이 생성은 성공한다. 기존 모델의 GLB는 아직 바꾸지 않는다(바꾸면 코·눈 승인 해시가 깨진다).
- undo·redo·초기화: 코와 같은 이력 스택이다. 초기화는 코·윤곽 값을 함께 지운다. 상담은 윤곽 후보를 만들지 않고 기존 윤곽 값을 유지한다.

### 얼굴형 볼륨 방향 (S15P31B204-583·584)

`contour.weight_shape`는 체중 수치나 건강 상태를 추정하지 않는 얼굴형 볼륨 미리보기다. 음수는 볼·턱선·목을 좁히고 양수는 넓힌다. `0`은 정확한 원본이며 공개 저장 범위는 `[-1, 1]`이다. GPU 워커가 두 방향의 안전한 끝값을 모델별로 검사한 뒤 GLB `contour.weight_shape_neg`·`contour.weight_shape_pos` 타깃을 굽는다. 검사 실패 또는 이전 모델에는 두 타깃을 넣지 않는다.

서버는 생성 결과의 GLB 타깃 쌍과 `asset.extras.live-mirror.weight_shape`의 모델 버전·fit 해시·양방향 검사 범위를 확인하고, 코 승인에 결속된 메시 해시와 일치할 때만 승인 정보를 저장한다. `GET /simulations/{simulationId}`의 `weightShapeSupported`는 이 승인 정보가 현재 모델과 일치할 때만 `true`다. 공통 `/morph-parameters` 카탈로그의 코드 존재만으로 모델 지원을 판단하지 않는다. 저장·undo·redo에서도 승인 상태를 다시 확인한다.

현재 단독 모프만 형상 검사했다. `contour.weight_shape`가 원본이 아닌 동안 다른 눈·코·윤곽 효과와 점 편집을 동시에 저장하지 않는다. 복합 최종 형상 검사를 마련한 뒤에만 이 제한을 넓힌다. 화면은 API 승인과 GLB 타깃 쌍이 모두 있을 때만 조절을 연다.

현재 PoC 생성 결과 10개의 `rig.json`에는 코 제한 20개와 눈 편집 shape 7종이 모두 존재한다. 이것은 **키 존재 검사**다. 자연스러움이나 실제 수술 가능성의 검증은 아니다. 같은 10개에서 `tip_projection` 하한 −10.1~−3.2, `tip_height` 상한 +5.3~+15로 달라 공통 DB 범위를 모델별 최종 허용량으로 사용할 수 없다.

## 서비스 대조 검증과 미결

1. “콧대를 조금 높여줘” → 같은 얼굴에서 채팅·슬라이더·점의 콧대 조절 방향과 저장 후 재조회한 After가 일치한다.
2. “양쪽 앞트임을 조금 해줘” → 승인된 눈 모델에서 양쪽 `eyeEdit`가 같은 거래로 바뀐다. “오른쪽만”은 미지원으로 안내한다.
3. “코끝을 앞으로 빼고 아래로 내려줘” → 돌출 증가와 높이 감소가 한 거래·undo 1회다.
4. “인아웃 쌍꺼풀” → 판정이 무쌍이고 범위가 승인된 눈에만 새 라인을 만든다. “콧구멍을 둥글게”는 미지원 안내이며 임의의 다른 효과를 적용하지 않는다.

**초기 구현과의 차이:** V3의 v1 시드는 코 3·눈 2개였고, V13에서 승인된 기존 코 리그에 필요한 코끝 저장 코드 2개를 추가했다. v2의 다른 눈·코 코드는 별도 카탈로그에 남는다. UI 표시 범위만 같다고 같은 얼굴 변형 강도를 보장하지 않으며, 모델별 승인과 최종 메시 검사로 실제값을 제한한다.

서비스 구현 담당자는 [눈·코 효과 v2 서비스 반영 안내](../../docs/plans/edit-effects-v2-adoption.md)의 순서와 공통 사례로 이 계약을 적용·검증한다.
